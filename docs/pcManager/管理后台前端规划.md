# 管理后台（PC 端）前端规划

> 项目：商场可视化智能车位/商铺导航系统
> 定位：与小程序端共用同一套后端 API（网关 8081），面向商场运营/平台管理员/商户的 PC 管理端
> 后端接口现状：126 个（auth 5 + business 121），全部 POST + JSON，已带 springdoc 中文注解

---

## 1. 技术选型

| 类别 | 选型 | 版本 | 理由 |
| --- | --- | --- | --- |
| 框架 | Vue 3 + TypeScript | Vue 3.5 / TS 5 | 国内团队熟悉度最高、中文生态好；Composition API 适合复杂编辑器状态 |
| 构建 | Vite | 6.x | 冷启动快，对 MapLibre 等 ESM 库友好 |
| UI 组件库 | Element Plus | 2.x | 后台管理标配，表格/表单/树/抽屉齐全，中文文档完善 |
| 状态管理 | Pinia | 2.x | 轻量、TS 友好；导航图编辑器需要 store 承载复杂画布状态 |
| 路由 | Vue Router | 4.x | 动态路由 + 路由守卫做 RBAC 菜单控制 |
| HTTP | Axios | 1.x | 统一拦截器：解包 `{code,message,data}`、自动带 `satoken` 头、401 跳登录 |
| 地图引擎 | **MapLibre GL JS** | 5.x | 导航图编辑器核心；开源、支持 GeoJSON source/layer、性能优于 Leaflet，可自定义 CRS |
| 图表 | ECharts | 5.x | 数据看板（二期） |
| 代码规范 | ESLint + Prettier | - | 统一风格 |

> 备选：若团队更熟 React，可等价替换为 React 18 + Ant Design 5 + Zustand，架构与接口对接完全不变。

**为什么地图用 MapLibre 而非 Leaflet**：导航图编辑器需要频繁增删改上千个点/边、拖拽交互、跨楼层图层切换、坐标标定换算，MapLibre 的 GeoJSON source 增量更新与 canvas 渲染性能明显更优；且完全开源无授权问题。

## 5. 导航图编辑器方案（核心模块）

### 5.1 总体思路：分层画布

编辑器 = 一个 MapLibre 地图实例 + 三个业务图层 + 交互工具条：

```text
┌─────────────────────────────────────────────┐
│ 工具条: 选择楼层 | 新建节点 | 连边 | 跨层 | 删除 | 路径预览 | 保存 |
├─────────────────────────────────────────────┤
│  MapLibre 画布                               │
│   └─ 底图层: 楼层平面图图片（标定后铺满画布）      │
│   └─ 空间层: zone/shop/space/poi GeoJSON(只读参考) │
│   └─ 导航层: nav_node(点) + nav_edge(线) + floor_connect(虚线) │
├─────────────────────────────────────────────┤
│ 右侧属性面板: 选中节点/边/跨层 → 编辑属性        │
└─────────────────────────────────────────────┘
```

### 5.2 坐标与标定（关键）

- 数据约定：楼层本地平面坐标（米，SRID 0）；后端几何接口出入参均为 GeoJSON
- **平面图标定**：首次使用上传平面图后，拖放 2 个标定点（如"电梯口 A/B"），输入其米制坐标 → 计算 `scale + offset`（+可选旋转），把像素坐标 ↔ 米制坐标换算存入 `mall_floor.remark`（JSON）
- 所有新增/移动节点的坐标，前端先换算成米制再调接口；从后端拉取的节点直接按米制渲染

### 5.3 核心交互

| 操作 | 交互 | 后端调用 |
| --- | --- | --- |
| 加载楼层 | 切换楼层 → 拉取该层节点/边 + 空间层 GeoJSON | nav-node/query + nav-edge/query + zone/shop/space get-geometry |
| 新建节点 | 点击画布 → 属性弹窗（类型 WAYPOINT/JUNCTION/电梯口/车位入口…、名称、是否可通行） | nav-node/with-geometry（带米制坐标点 GeoJSON） |
| 移动节点 | 拖拽 → 松开后写入 | nav-node/update-geometry |
| 新建边 | 工具条"连边"→ 点起点 → 点终点 → 属性弹窗（WALK/电梯/扶梯、双向、权重）→ distance_m 前端按两节点坐标欧氏距离自动算 | nav-edge/create |
| 跨层连接 | 选中节点 → "创建跨层" → 选择目标楼层 + 目标节点 → 折算成本 | floor-connect/create |
| 删除 | 选中节点/边 → 删除（确认后，节点先检查是否有边引用） | nav-edge/delete / nav-node/delete |
| 路径预览 | 选起终点节点 → 高亮最短路径 + 显示分段距离 | nav/route |
| 保存策略 | **即时保存**：每次操作立即调接口（简单可靠）；编辑器内维护"已变更"角标 | - |

### 5.4 状态管理（Pinia `editor` store）

```ts
interface EditorState {
  mallId: number; floorId: number;
  floorImage?: { url: string; calibration: { scale: number; offset: [number, number] } };
  nodes: NavNode[];            // 当前楼层节点（含 geom）
  edges: NavEdge[];
  connects: FloorConnect[];
  selected: { type: 'node'|'edge'|'connect'; id: number } | null;
  tool: 'select'|'create-node'|'create-edge'|'connect-floor'|'delete';
  dirty: boolean;
}
```

### 5.5 数据一致性要点

- 节点/边删除顺序：先删引用该节点的边，再删节点（后端无物理外键，前端保证）
- 边 distance_m：前端按 `Math.hypot(dx, dy)` 计算（米制同单位），与后端 `ST_Distance` 一致
- 跨层连接的 from/to 节点必须存在于对应楼层（前端下拉只列目标楼层节点）
- 车位/商铺入口节点（SPACE_ENTRY/SHOP_ENTRY）类型：创建时 name 可自动带 `车位号/商铺名`，便于运营识别
